## AI Engineering

### Structured LLM Outputs (Schema-Enforced JSON)
- **Location**: [`src/boardgamerules/ai/generator.py:39`](src/boardgamerules/ai/generator.py#L39)
- **Why & How**: Guarantees that the LLM produces valid, type-safe JSON matching a pre-defined schema. Rather than parsing free-form Markdown with fragile regular expressions, the model's generation tokens are constrained directly by the Gemini engine to match the required fields and types.

### Prompt Injection Defense (System vs. Data Separation)
- **Location**: [`src/boardgamerules/ai/prompts.py:22`](src/boardgamerules/ai/prompts.py#L22)
- **Why & How**: Untrusted user questions and third-party PDF rulebook contents are isolated inside structured XML delimiter tags (<rulebook_excerpts>, <user_question>). The system instruction directs the model to treat content within these tags strictly as passive reference data rather than executable instructions, and all special XML characters and control characters are escaped.

### Data Ingestion Pipeline (Extract -> Chunk -> Embed -> Index)
- **Location**: [`src/boardgamerules/batch/ingestor.py:54`](src/boardgamerules/batch/ingestor.py#L54)
- **Why & How**: "Ingestion" (taking in and digesting data) turns a raw PDF rulebook dropped in incoming/ into searchable database records: read the PDF bytes, pull out each page's text, split it into overlapping RuleChunks, store their vector embeddings in Qdrant, and save the GameManual as READY in the database.

### Retrieval-Augmented Generation (RAG) Vector Port
- **Location**: [`src/boardgamerules/domain/contracts.py:96`](src/boardgamerules/domain/contracts.py#L96)
- **Why & How**: Decouples the vector store (Qdrant) from the rest of the application. The RAG port only indexes, searches, and deletes RuleChunks scoped by canonical game_id metadata filters.

### Tiered Source Attribution & Verification Badge
- **Location**: [`src/boardgamerules/domain/manual.py:21`](src/boardgamerules/domain/manual.py#L21)
- **Why & How**: When Tier-3 AI fallback generates rules because no official PDF was found, we cache them with source=AI_GENERATED (is_verified=False). When an official PDF arrives later, the AI version is marked SUPERSEDED so verified ground-truth rules take precedence.

### Grounded Citation & Chunk Metadata
- **Location**: [`src/boardgamerules/domain/rag.py:12`](src/boardgamerules/domain/rag.py#L12)
- **Why & How**: Storing page_number and section_title alongside each vector chunk allows the RAG system to cite exact rulebook pages in its answers, reducing hallucination and building user trust.

### Search-Grounded URL Discovery (Grounding Metadata)
- **Location**: [`src/boardgamerules/fetcher/search_provider.py:25`](src/boardgamerules/fetcher/search_provider.py#L25)
- **Why & How**: "Grounding" means anchoring an AI model's answer in verifiable real-world facts rather than letting it guess from memory (which often hallucinates broken links). With Google Search grounding enabled, Gemini attaches `grounding_chunks` metadata containing the actual web pages and PDF URLs returned by Google Search. We extract and prioritize these verified grounding links ahead of any unverified URLs mentioned in the generated text.

### Section-Aware Overlapping Chunking
- **Location**: [`src/boardgamerules/rag/chunker.py:37`](src/boardgamerules/rag/chunker.py#L37)
- **Why & How**: Splitting rulebooks purely by fixed character counts cuts rules mid-sentence and loses the heading context (e.g., whether a rule belongs to "Setup" or "End of Game"). Tracking active section headers and sliding with overlap keeps rules coherent for vector retrieval.

### Vector Embeddings (Translating Text Meaning into Coordinates)
- **Location**: [`src/boardgamerules/rag/embeddings.py:28`](src/boardgamerules/rag/embeddings.py#L28)
- **Why & How**: An "embedding" is a list of floating-point numbers (e.g., 768 numbers between -1.0 and 1.0) that represents the meaning of a text as a point in multi-dimensional space ("embedding" the text into a coordinate space). Texts with similar meaning get placed at nearby coordinates even when they share zero keywords, allowing Qdrant to find relevant rules by measuring distance (Cosine Similarity) between a player's question vector and rule vectors.

### Asymmetric Task-Type Embeddings (Document vs. Query)
- **Location**: [`src/boardgamerules/rag/embeddings.py:35`](src/boardgamerules/rag/embeddings.py#L35)
- **Why & How**: Modern embedding models optimize vector representations differently for long rulebook passages being indexed (RETRIEVAL_DOCUMENT) versus short user questions (RETRIEVAL_QUERY). Separating embed_documents and embed_query preserves this distinction at the contract boundary.

### Asynchronous Worker Pipeline Offloading
- **Location**: [`src/boardgamerules/rag/ingestion.py:16`](src/boardgamerules/rag/ingestion.py#L16)
- **Why & How**: Extracting text from multi-page PDFs and chunking text with regexes is CPU-intensive. Running it in a background thread via asyncio.to_thread prevents blocking the main event loop, keeping async web services responsive while processing documents.

### Page-Preserving PDF Extraction for Grounded Citations
- **Location**: [`src/boardgamerules/rag/pdf_extractor.py:19`](src/boardgamerules/rag/pdf_extractor.py#L19)
- **Why & How**: Extracting text page-by-page with 1-based page numbers ensures every downstream vector chunk retains its exact source page number for verifiable user citations.

### Grounded RAG Question-Answering Pipeline
- **Location**: [`src/boardgamerules/rag/qa.py:34`](src/boardgamerules/rag/qa.py#L34)
- **Why & How**: Rather than asking an LLM to answer board game rules from its pre-training memory (which often hallucinates house rules or wrong editions), the RAG pipeline first retrieves the top-k relevant rulebook chunks from the vector store. If no chunks exist for the game, it fails fast with ManualNotFoundError so the caller can trigger a verified fallback rather than letting the LLM guess without context.

### Metadata-Filtered Vector Retrieval (Multi-Game Isolation)
- **Location**: [`src/boardgamerules/rag/qdrant_engine.py:46`](src/boardgamerules/rag/qdrant_engine.py#L46)
- **Why & How**: All board games share one Qdrant vector collection partitioned by a keyword index on game_id. Every semantic search and deletion applies a strict Filter(must=[FieldCondition(key="game_id")]) so chunks from one board game never bleed into another game's rule answers.

## Design Pattern

### Anti-Corruption Layer (Pydantic Schema to Domain Mapper)
- **Location**: [`src/boardgamerules/ai/schemas.py:62`](src/boardgamerules/ai/schemas.py#L62)
- **Why & How**: External LLM responses arrive as unvalidated JSON dictionaries. Using Pydantic models as an intermediate parsing layer and mapping them through explicit sanitizers insulates the pure domain layer from malformed outputs, strips whitespace, drops empty items, and prevents hallucinated citation IDs from corrupting verified rulebook citations.

### Gateway & Repository (Injected Interfaces)
- **Location**: [`src/boardgamerules/batch/ingestor.py:29`](src/boardgamerules/batch/ingestor.py#L29)
- **Why & How**: PdfBatchIngestor does not talk to your hard drive, Qdrant, or MongoDB directly. Instead, those tools are passed in through BatchIngestionDependencies: PdfStorage and RagEngine are Gateways (wrappers around external tools like folders and Qdrant), while PendingPdfRepository and GameManualRepository are Repositories (wrappers for saving and loading database records). Because the ingestor only calls methods like self._storage.list_unprocessed_keys(), we can swap local folders for cloud storage or MongoDB for an in-memory test database without changing the ingestor code.

### Collecting Parameter Pattern
- **Location**: [`src/boardgamerules/batch/ingestor.py:191`](src/boardgamerules/batch/ingestor.py#L191)
- **Why & How**: Instead of passing three separate lists (processed, duplicates, failed) into every helper function, we create one _BatchRunTracker and pass it through the loop to collect results. When the loop finishes, to_result() converts those lists into a read-only BatchIngestionResult.

### In-Memory Fake Repository
- **Location**: [`src/boardgamerules/db/in_memory.py:18`](src/boardgamerules/db/in_memory.py#L18)
- **Why & How**: Unlike brittle unittest.mock patches that assert how a database driver was called, an in-memory Fake implements the real repository contract (including uniqueness constraints, sorting, and auto-superseding) so service and API tests run in microseconds without Docker.

### Data Mapper Pattern (vs. Active Record / ODM)
- **Location**: [`src/boardgamerules/db/mappers.py:28`](src/boardgamerules/db/mappers.py#L28)
- **Why & How**: Unlike Active Record ODMs (like Beanie or MongoEngine) where domain models inherit from a database Document class and call `await model.save()`, a Data Mapper translates between pure domain dataclasses and raw MongoDB "_id" dicts. This keeps domain logic vendor-agnostic (easy to swap MongoDB for GCP Firestore or InMemory fakes) and testable without a DB.

### Explicit Abstract Base Class (ABC) Ports (Hexagonal Architecture)
- **Location**: [`src/boardgamerules/domain/contracts.py:21`](src/boardgamerules/domain/contracts.py#L21)
- **Why & How**: Defining abstract base classes in the inner domain layer without importing concrete drivers (MongoDB, Qdrant, GCS, Gemini) makes every adapter's contract immediately visible on its class definition line (e.g., `class QdrantRagEngine(RagEngine):`) and fails fast at instantiation time if any required @abstractmethod is missing.

### Interface Segregation Principle (ISP)
- **Location**: [`src/boardgamerules/domain/contracts.py:27`](src/boardgamerules/domain/contracts.py#L27)
- **Why & How**: Instead of forcing every service to depend on a single giant database interface, we split persistence into 4 focused repository interfaces (User, GameManual, PendingPdf, UserHistory). The Batch PDF Job only needs PendingPdfRepository + GameManualRepository, keeping mocks tiny.

### Composite Interface Facade
- **Location**: [`src/boardgamerules/domain/contracts.py:82`](src/boardgamerules/domain/contracts.py#L82)
- **Why & How**: Combining the 4 segregated repository interfaces into a single composite NoSqlRepository interface lets the DI container pass one unified database adapter when needed, while individual consumers still type-hint only the narrow sub-interface they require.

### Domain Exception Hierarchy
- **Location**: [`src/boardgamerules/domain/exceptions.py:6`](src/boardgamerules/domain/exceptions.py#L6)
- **Why & How**: Defining a single base domain exception (BoardGameRulesError) with specific subclasses lets higher layers (like FastAPI exception handlers) map domain failures cleanly to HTTP status codes (e.g., 400, 404, 502) without coupling domain code to HTTP frameworks.

### Immutable State Machine Transition
- **Location**: [`src/boardgamerules/domain/manual.py:57`](src/boardgamerules/domain/manual.py#L57)
- **Why & How**: Instead of mutating self.status in place, transition methods return a new frozen instance via dataclasses.replace(), preserving Command-Query Separation and history safety.

### Value Object & Immutable Entity
- **Location**: [`src/boardgamerules/domain/user.py:18`](src/boardgamerules/domain/user.py#L18)
- **Why & How**: Using @dataclass(frozen=True) makes domain entities thread-safe, hashable, and predictable: functions cannot secretly mutate shared state as objects pass through the pipeline.

### Strategy Pattern (Pluggable Log Formatters)
- **Location**: [`src/boardgamerules/logging_config.py:59`](src/boardgamerules/logging_config.py#L59)
- **Why & How**: ConsoleLogFormatter and GcpJsonLogFormatter share Python's logging.Formatter interface, so the app can switch between human-readable local output and GCP Cloud Logging JSON using one environment variable without changing a single log statement in the codebase.

### Parameter Object (Dependency Injection Bundle)
- **Location**: [`src/boardgamerules/orchestrator/models.py:21`](src/boardgamerules/orchestrator/models.py#L21)
- **Why & How**: Bundling multiple collaborating services and configuration objects into a single immutable dataclass prevents long, fragile constructor signatures (known as the "Long Parameter List" code smell). It simplifies wiring dependencies in DI containers and testing with mock/fake adapters.

### Facade & Chain of Responsibility (3-Tier Rule Resolution)
- **Location**: [`src/boardgamerules/orchestrator/service.py:40`](src/boardgamerules/orchestrator/service.py#L40)
- **Why & How**: RuleOrchestrator acts as a simplified entry-point (Facade) hiding multi-database, vector store, web search, and LLM complexity. It coordinates a Chain of Responsibility across three tiers: Tier 1 checks local cache (MongoDB/Qdrant); if missing, Tier 2 attempts online search and PDF ingestion; if unavailable, Tier 3 falls back to schema-constrained generative AI.

## System Design

### Dead-Letter Folder (Isolating Broken Files)
- **Location**: [`src/boardgamerules/batch/ingestor.py:60`](src/boardgamerules/batch/ingestor.py#L60)
- **Why & How**: One broken or unreadable PDF must not stop the batch job from processing the other PDFs in incoming/. When a single file fails, we move it into failed/ (a "dead-letter" folder) and save the error message in the database, then continue with the remaining files.

### Moving Files by Status (incoming/ -> processed/ or failed/)
- **Location**: [`src/boardgamerules/batch/storage.py:19`](src/boardgamerules/batch/storage.py#L19)
- **Why & How**: Moving each PDF out of incoming/ as soon as it finishes ensures the batch job never processes the same file twice if it restarts, and keeps broken PDFs separated in failed/ instead of retrying them forever.

### Single-Active-Record Invariant (Auto-Superseding)
- **Location**: [`src/boardgamerules/db/in_memory.py:44`](src/boardgamerules/db/in_memory.py#L44)
- **Why & How**: When a new READY manual is saved for a (game_id, edition), any previously READY manual for that same game and edition (such as an earlier Tier-3 AI fallback) is automatically transitioned to SUPERSEDED so queries never return stale unverified rules.

### UTC Timezone Normalization at Persistence Boundary
- **Location**: [`src/boardgamerules/db/mappers.py:18`](src/boardgamerules/db/mappers.py#L18)
- **Why & How**: MongoDB stores timestamps in UTC but deserializes BSON Date values as timezone-naive datetime objects by default. Attaching UTC at the mapper boundary guarantees domain entities always receive timezone-aware UTC timestamps.

### NoSQL Operator Injection Prevention
- **Location**: [`src/boardgamerules/db/mongo.py:40`](src/boardgamerules/db/mongo.py#L40)
- **Why & How**: In MongoDB, passing a dict like {"$ne": None} as a filter value executes a query operator instead of a literal equality check (CWE-943). Enforcing strict scalar types (str/int) at the repository query boundary blocks operator injection even if upstream validation is bypassed.

### Exception Translation at Infrastructure Boundary
- **Location**: [`src/boardgamerules/db/mongo.py:56`](src/boardgamerules/db/mongo.py#L56)
- **Why & How**: Catching low-level driver exceptions (PyMongoError) and re-raising a domain exception (StorageOperationError) prevents database driver details from leaking into business logic.

### Asynchronous I/O for High-Concurrency LLM Workloads
- **Location**: [`src/boardgamerules/domain/contracts.py:14`](src/boardgamerules/domain/contracts.py#L14)
- **Why & How**: Unlike traditional CRUD apps (where DB queries take ~3ms), AI/RAG workloads wait 2-8 seconds on external LLM generation, embedding APIs, and vector searches. Using async def contracts allows a single GCP Cloud Run container's event loop to serve hundreds of concurrent users waiting on I/O without blocking OS threads or spinning up costly extra containers, and enables parallel I/O fan-out via asyncio.gather().

### Cloud-Agnostic Blob Storage Abstraction
- **Location**: [`src/boardgamerules/domain/contracts.py:140`](src/boardgamerules/domain/contracts.py#L140)
- **Why & How**: Cloud Run containers have ephemeral filesystems. Abstracting PDF file operations behind PdfStorage lets local development use a local directory while GCP Cloud Run Jobs use a Google Cloud Storage (GCS) bucket with zero changes to the batch ingestion logic.

### Content-Addressable Deduplication (SHA-256)
- **Location**: [`src/boardgamerules/domain/validators.py:44`](src/boardgamerules/domain/validators.py#L44)
- **Why & How**: Hashing raw PDF bytes with SHA-256 produces a deterministic 64-char fingerprint. Checking this hash before chunking or embedding guarantees the same rulebook PDF is never ingested twice, even when uploaded under different filenames or fetched from mirror URLs.

### Path Traversal Defense-in-Depth
- **Location**: [`src/boardgamerules/domain/validators.py:54`](src/boardgamerules/domain/validators.py#L54)
- **Why & How**: Validating storage keys inside the domain model prevents malicious inputs like "../../etc/passwd", null bytes, or absolute paths from reaching filesystem or blob adapters.

### Canonical Identifier Normalization
- **Location**: [`src/boardgamerules/domain/validators.py:68`](src/boardgamerules/domain/validators.py#L68)
- **Why & How**: Because both MongoDB (document metadata) and Qdrant (vector chunk filters) partition data by game_id, normalizing arbitrary user input ("Settlers of Catan!") into a deterministic slug ("settlers-of-catan") prevents duplicate silos and cache misses across databases.

### SSRF Protection (Blocking Private Networks & Cloud Metadata)
- **Location**: [`src/boardgamerules/fetcher/url_safety.py:20`](src/boardgamerules/fetcher/url_safety.py#L20)
- **Why & How**: When a server downloads URLs discovered on the internet, an attacker could supply a link pointing to localhost (127.0.0.1) or GCP's internal metadata server (169.254.169.254) to steal cloud credentials. Before every download and every redirect hop, we check the scheme, port, and resolved IP addresses to make sure we only connect to public internet servers.

### Twelve-Factor Logging & Standard Streams (stdout -> GCP Cloud Logging)
- **Location**: [`src/boardgamerules/logging_config.py:27`](src/boardgamerules/logging_config.py#L27)
- **Why & How**: Instead of writing log files to disk or calling a remote logging server over the network, the app writes logs directly to standard streams (stderr for local console, stdout for GCP JSON). Cloud Run automatically reads every JSON line from stdout and turns fields like "severity", "message", and "game_id" into searchable entries in GCP Cloud Logging.

### Single-Flight Per-Key Concurrency Lock
- **Location**: [`src/boardgamerules/orchestrator/service.py:58`](src/boardgamerules/orchestrator/service.py#L58)
- **Why & How**: When multiple concurrent requests demand the same uncached game rulebook simultaneously, acquiring a per-game lock with double-checked caching ensures the system fetches, chunks, and indexes the document only once instead of causing duplicate API calls or race conditions.

### Twelve-Factor Externalized Configuration & Fail-Fast Startup
- **Location**: [`src/boardgamerules/rag/config.py:29`](src/boardgamerules/rag/config.py#L29)
- **Why & How**: Rather than hardcoding server URLs, model names, or collection names inside config code, all settings are read strictly from environment variables (.env locally, OS env in production) and validated at startup so missing configuration fails fast.

### Rate-Limit Backoff & Retry (HTTP 429 Resource Exhausted)
- **Location**: [`src/boardgamerules/rag/embeddings.py:47`](src/boardgamerules/rag/embeddings.py#L47)
- **Why & How**: Cloud LLM and embedding APIs enforce strict per-minute token/chunk quotas (e.g., 100 embedded chunks per minute on Google AI Studio's free tier). Catching 429 RESOURCE_EXHAUSTED responses, honoring the server's requested retry delay, and retrying automatically allows large multi-manual batch jobs to complete smoothly without dropping files into failed/.

### Resource Exhaustion & PDF Bomb Defense
- **Location**: [`src/boardgamerules/rag/pdf_extractor.py:38`](src/boardgamerules/rag/pdf_extractor.py#L38)
- **Why & How**: Enforcing byte-size and page-count upper bounds before iterating over a PDF stream protects stateless containers from out-of-memory crashes caused by malicious or abnormally large external rulebook files.

### Embedded In-Memory Database Engine vs. Hand-Rolled Fake
- **Location**: [`src/boardgamerules/rag/qdrant_engine.py:39`](src/boardgamerules/rag/qdrant_engine.py#L39)
- **Why & How**: Unlike MongoDB (which requires a separate server process and therefore needed a hand-rolled InMemoryNoSqlRepository fake for unit tests), Qdrant's client ships with a built-in embedded engine via AsyncQdrantClient(location=":memory:"). Passing ":memory:" in tests exercises the exact same QdrantRagEngine filter AST, UUID mapping, and payload serialization code that runs in production against Qdrant Cloud/Docker, without maintaining a second vector engine.

### Deterministic UUIDv5 Point IDs for Idempotent Vector Upserts
- **Location**: [`src/boardgamerules/rag/qdrant_engine.py:178`](src/boardgamerules/rag/qdrant_engine.py#L178)
- **Why & How**: Qdrant requires point IDs to be UUIDs or unsigned 64-bit integers. Hashing "{game_id}:{chunk_id}" with UUIDv5 produces a deterministic UUID so re-indexing a manual overwrites existing points in place instead of creating duplicate chunks.
